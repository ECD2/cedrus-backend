## The three proofs

### A2 — a write against another person's record is refused

**Programs path** (real `publishProgramRevision` → real `publish_program_revision()` on
PGlite with the real migrations):

- B publishes a *changed* source under A's exact kind and title. It resolves, but on a
  DIFFERENT program owned by B; A's program is byte-identical before and after
  (revision count, item count, `current_revision_id`, owner). The identical bytes A
  published are then accepted for B as revision 2 of B's own program — the
  idempotency key is per program, so a shared source is never a cross-owner refusal.
- A revision for B naming A's `program_id`, inserted as `service_role` (which bypasses
  RLS), is refused by the database with 23503 from the composite owner FK. **Control:**
  the identical insert for A against A's own program succeeds. An item for B on A's
  revision is refused the same way.
- Signed in as B, A's program is invisible (0 rows); **control:** signed in as A, 1 row.

**CoS writeback path** (real `runCosDailyBrief` in writeback-only mode → real
`writeBriefToCos` / `resolveCosUserId` / `buildBriefRow`, with the single supabase-js
insert replaced by a real INSERT into a PGlite `cos.today_briefs`):

- The job runs for B while the deployment's `COS_USER_ID` names A — today's production
  shape. Exactly one new row appears, owned by B, with B's summary; A's pre-existing row
  is byte-identical; every CoS read the job made was scoped to B; B's brief cites B's
  record id and not A's. **Control:** the same run for A writes A's row and leaves B's
  untouched.
- Pinned on the real function: a named caller is returned as named (never the env's A);
  with nobody named the env's A is returned. `cosInsertTodayBrief` still refuses an
  ownerless row before any client exists.

A write for B *naming* A's row cannot be expressed through this path: the row's owner
is the resolved caller, and nothing in the request can move it. That is the same
"inexpressible, not discouraged" shape as A4.

### A5 — the public key reads nothing

- Tables are ENUMERATED FROM THE MIGRATION FILES (every `create table if not exists`,
  plus every pre-existing table a migration `alter table`s): `admin_audit, app_users,
  program_items, program_revisions, programs, user_capabilities, user_settings`. The
  list is asserted COMPLETE against the catalog: every public table with a `*user_id*`
  column is on it, and nothing else is.
- The fixture reproduces Supabase's stock default privileges (anon gets ALL on every
  new public table). **Self-check:** an unprotected throwaway table IS readable by anon
  under that fixture (1 row), so the refusals below are refusals, not a role that can
  read nothing.
- With the role set to `anon`, every one of the seven returns **permission denied
  (42501)**. **Control:** `service_role` reads every row of each (3 / 1 / 1 / 1 / 2 / 2 /
  138). Beside behaviour, structure: no policy names anon/public and anon holds no
  SELECT/INSERT/UPDATE/DELETE, per table, by name. Authenticated with no JWT reads 0
  rows of `user_settings`; the person provisioned through the real
  `provision_user()` reads their own 1 row.
- The eight CoS tables (`READABLE_TABLES`) are enumerated and ANNOUNCED AS NOT
  RE-VERIFIED by the suite — their DDL is in the CoS project. See "Live facts".

current_app_user_id()`) is NULL for anon. A leaked policy that still carries the owner
predicate is caught only by the structural check — which is why the suite asserts both.

### A10 — no person's identifier appears in another person's log trace

- The real job runs twice in one process, A then B, in LIVE mode with a transport that
  throws after the wire might have been touched — the one path on which the job names
  the ledger key, and the key carries the person's id. Each run is wrapped in exactly
  the correlation context `scheduler.guard()` sets. Every console line is captured and
  parsed as the JSON the logger emits.
- Every line carries one of the two correlation ids (no shared, unattributed line).
  A's id appears in NO line carrying B's id, and vice versa. **Controls:** each trace is
  non-empty (5 lines) and DOES carry its own person's id, on `cos.send.failed` naming
  that person's ledger row — an empty log fails.
- The same, with the two runs INTERLEAVED (A's gather slow, B's fast; B's failure line
  precedes A's in the capture). This is the variant that sees a context leak.
